# agent-workflow-v1.1

Use only when the user explicitly selects agent-workflow-v1.1 for this run; implicit invocation is disabled. A current explicit invocation instructs the main agent to start AGWF in the same turn for the user's authorized scope, including preparation and small tasks. It re-enables that scoped run after an earlier disablement; historical selection or another session does not. Discussion, quotation, inspection or maintenance of this skill is not a request to resume stopped project work. The main chat is the main coordinator: it owns delivery, state writes and all real agent dispatches. Its model and effort are selected by the user in the client; this skill assigns neither. Keep small tasks on the main agent after startup; a team is optional, startup and monitoring are not.

## Required startup on explicit invocation

Before substantive research, project changes, tests or delegation, obtain a fresh native usage receipt and execute startup through the pinned candidate. Use authorized `workflow activate`/`bind-active-goal` when its evidence exists. If the user has limited work to preparation, forbidden native goal creation, or supplied no active goal, start the integrated watcher through the manual path in [operations](references/operations.md) and keep work within the authorized scope. Do not create a native goal without explicit permission. Loading the skill, enabling its selector or checking usage once does not fulfill startup.

Verify actual startup: a fresh healthy sample and a live owned watcher for the selected run/epoch; for a full workflow also verify active workflow state. Report the startup result before substantive work. Reuse an existing healthy run within the same authorized scope instead of creating duplicate workers. A later explicit invocation can authorize the existing resume/new-epoch path after a stop; retain the exact user event and all recovery checks.

If startup is refused, evidence is unavailable, or limits require `SAVE_AND_STOP`, immediately report the concrete reason and perform only necessary recovery. Do not silently continue the requested work directly on the main agent. A later stop overrides startup; inspecting or updating this skill while stopped does not resume the previous assignment.

Use the pinned `scripts/candidate.py` entry for workflow commands, coordination and its integrated limit watcher. The entry also runs directly from a terminal with its approved manifest pin; neither skill invocation nor a watcher call is a prerequisite for executing it. Direct core CLIs are unsupported and refuse. Read [runtime binding](references/coexistence.md) for the external trust anchor and isolated run contract. Read [operations](references/operations.md) when starting a run. Role TOMLs and `private/limit-watcher/role.json` are the source of model settings. The watcher engine, instructions and role are maintained, packaged and verified inside this skill; there is no separate limit-watcher skill or launcher.

## Role skills and memory

Each defined subagent has its own `SKILL.md` and `MEMORY.md`: `roles/<role>/` for coordinator, architect, implementer, researcher and verifier; `private/limit-watcher/` for limit_watcher. Role definitions explicitly reference their own documents. The runtime includes only that role's skill and memory in the prepared assignment; a missing or empty document refuses loading. Temporary specialists inherit their base role's documents along with the task's domain-specific instructions.

Each role skill has its own explicit-only invocation policy. Role skills are internal assignment instructions, not independent entry points: direct selection without a prepared role assignment and matching actual model/effort evidence must stop with the missing evidence. They never activate AGWF or start monitoring. Disabling the workflow requires disabling all seven skill entries and stopping owned workers; an update does not re-enable them.

Role memory is persistent reference material, not permission or a replacement for current project evidence. Start with no invented past observations. Return proposed memory additions to the main agent; it reviews them and publishes maintained documents between runs. Role documents are included in the package manifest, so a memory change follows the normal package update and fresh-run binding. Never edit the installed skill during a live task.

## Integrated limit watcher

An authorized `workflow activate` or `bind-active-goal` through the pinned candidate starts the integrated model-free watcher automatically. Before activation, obtain a real `mcp__codex_app__get_usage_limits` receipt from the existing Codex connection and supply it with `--usage-input`; follow the [native usage contract](references/native-usage.md). The watcher never starts a Codex app-server, chooses a CLI from PATH or connects to another transport. The candidate verifies a healthy, fresh sample before committing active workflow state; missing or expired receipts refuse activation. `resume` requires the same fresh receipt plus a new epoch. For a recorded `usage_receipt_expired` halt, use the telemetry recovery path below; other stops require direct user continuation or the accepted native-goal transition.

The main coordinator refreshes the native receipt by the adaptive 300/120/60/30-second deadline during authorized work. The background Python worker validates supplied readings and fails closed when fresh data is absent; it cannot call the host tool itself. Re-reading a file never refreshes its observation time. Active commands renew the 600-second lease; unhealthy monitoring blocks new work while recovery remains available. `complete` and `halt` stop the owned worker and verify exit. Heartbeats check run/epoch ownership without hashing the package; full dependency checks occur at command and measurement boundaries. Use `workflow status` at work boundaries; a quiet chat does not renew data or lease. Explicit selection requires the main agent to execute and verify startup; the client has no automatic process-launch hook. Manual `watcher start/ingest/status/renew/stop` follow the same receipt and authorization contract.

At 25% remaining, prepare a verified checkpoint of completed work; at 20% or an early recovery signal, stop new work, obtain short acknowledgements from active writers, verify required files and stop only owned workers. Missing usage is unknown: retry once, then save and stop. `SAVE_AND_STOP` requires immediate action by the main coordinator without waiting for an agent. A stale measurement is a technical interruption, not proof of exhausted quota or revoked user permission. After saving and halting, a recorded `usage_receipt_expired` may recover under the existing authorized, active native goal using `resume` with `usage_recovery: true`, a fresh actual usage receipt, fresh same-goal observation/inventory, unchanged verified checkpoint and stopped owned workers. The candidate records the actual watcher cause during `halt`; it refuses quota/early-reserve/other failures, explicit user stops and inactive goals on this path. Do this recovery when evidence is available; do not demand another typed continuation solely because telemetry expired or a paused state was not observed. Do not mark the native goal `blocked` solely for telemetry expiry; follow the native goal tool's blocked criteria. This restores monitoring and the helper, not the native goal's status, and creates no invented user quote or UI event. Other stops retain their continuation requirements; never redeem a reset or change native goal status automatically. A weekly-window exception requires the user's actual quote and bounded expiry; measurements still retain both windows. Only ambiguous recovery decisions may use the integrated `limit_watcher` role, exactly `gpt-6.1-terra`/`medium`; if unavailable, report the gap. See [operations](references/operations.md) and [watcher role](private/limit-watcher/limit_watcher.md).

Use the [selective context and acceptance contract](references/context.md) for bounded current-state handoffs. Keep original authority timestamps, pinned evidence references and reviewer counterevidence. Renderings never authorize dispatch or promise cache benefits. Native execution completion and independent artifact acceptance are distinct versioned observations; run the model-free producer gate before consequential independent review.

Give a child the objective, necessary inputs, allowed write paths and acceptance criteria. Start with a fresh context, not a copy of the main conversation. Name implementer sessions by their actual work, such as frontend, backend, editor or data_analysis. Use relevant existing project skills rather than manufacturing permanent domain roles. For niche project work, create a temporary specialist from the appropriate base role with a specific name, domain instructions, necessary sources/tools and acceptance criteria; no pre-existing domain role or separate user invocation is required.

Researcher gathers and synthesizes evidence. Implementer designs, builds and fixes. Verifier independently checks consequential results. Architect resolves expensive design choices or technical disagreement, not every task. Mechanical repeatable work belongs in scripts. Reuse an existing suitable script first; otherwise create and validate a project-local script when repetition or reliability justifies it, then reuse it. This is task-driven agent judgment, not an idle background scheduler. No standing Admin or Executor layer.

Keep one writer per file. Specialists agree on shared interfaces before changing them. Verify security, authentication, potential data loss, shared APIs and broad behavior changes independently; the main coordinator can verify narrow reversible work. Return conclusions, changed paths and evidence rather than raw logs.

Respect the user's current authorization and project restrictions. Stop instructions cancel further dispatch until explicit continuation. Keep only current work and durable decisions; remove owned temporary material only after recovery dependencies are closed. No arbitrary message-length cap or mandatory meetings.

The helper validates operations that pass through it; it does not intercept native tools or automatically stop processes. The main coordinator must execute the returned tool calls, record their results, and inspect real live inventory. Never claim a requested model is an observed effective model without metadata.

## Coordination

Before dispatching substantial work with dependent specialist domains, ask the `coordinator` subagent for task division, dependencies, specialist selection, proposed file ownership and acceptance criteria. Also consult it after a material scope change, unresolved conflict between specialist results, or repeated failure requiring a new plan. Small/independent tasks and routine tracking stay with the main coordinator.

Send the objective, current constraints, findings and relevant source locations with a fresh context. The coordinator returns a read-only plan; it neither spawns agents nor writes workflow state. The main coordinator checks user constraints and feasibility, records accepted tasks and executes the plan without duplicating it. Link plan-dependent work through `depends_on` to the accepted coordination task. Minor capacity/file adjustments stay with the main coordinator; return only consequential strategy changes to the coordinator. Architect decides technical design, The planning coordinator decides how work is organized. Stop waiting on completed sessions; use a new bounded coordination task when needed. If the exact model/effort is unavailable, report the gap and hold plan-dependent work; independent authorized work may continue. Recovery never waits for a planning agent.


## User model policy (27 October 2026)

Workflow roles may use only `gpt-6.1-sol`, `gpt-6-astra`, or `gpt-6.1-terra`. Reasoning must be `medium` or higher; `none`, `minimal`, and `low` are forbidden for every role. Role files pin the model and default effort; no automatic fallback or model substitution. The retired `astra_coordinator` role must not be restored. The integrated `limit_watcher` role uses `gpt-6.1-terra`/`medium` only. The main client model and effort belong to the user; this skill does not choose or change them.
