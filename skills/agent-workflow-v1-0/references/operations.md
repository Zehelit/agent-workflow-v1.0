# Operation

Python 3.11+; standard library only. Use `python -X utf8 -B scripts/candidate.py --help`. Read [runtime binding](coexistence.md) and preserve the external build-receipt manifest SHA before starting. Use the host's bundled Python if `python` is unavailable. Commands consume JSON via `--input path` or stdin. State lives at `<project>/.agent-workflow-v1-0/runs/<run-id>/state.json`; checkpoints, locks, temporary data, watcher ownership and coordination journals use this same isolated run namespace; only the main coordinator writes it. Files, test artifacts and snapshots are never normal prompt input.

## Start and dispatch

An explicit invocation requires startup in the same turn, before substantive work, even for preparation or small tasks. It is not merely a request to load these instructions. If native goal creation is outside the authorized scope, use manual monitoring instead of skipping startup; do not manufacture a goal or binding evidence. Discussion or maintenance of the skill does not resume a stopped assignment.

For work outside an activated workflow, select a fresh run ID and use the pinned candidate's `watcher start --usage-input USAGE.json`. This starts monitoring only; it does not activate workflow state or authorize agents. Inspect `watcher status` until it confirms a fresh healthy sample and a live owned worker for this run/epoch, or reports a refusal. Use `watcher ingest` for subsequent real usage readings and `watcher renew` at work boundaries; finish with `watcher stop` and verify exit. A healthy matching existing run can be reused. A stopped run needs its accepted continuation/new-epoch path and all recovery checks, not a duplicate worker to bypass the stop. Report the observed startup result before doing the requested work; if startup fails or requests `SAVE_AND_STOP`, report the reason and hold substantive work.

Read [native usage receipts](native-usage.md) before activation or resuming. The main agent supplies a current reading from the existing `mcp__codex_app__get_usage_limits` tool with `--usage-input`. Background monitoring reads that receipt; it never launches a Codex app-server and cannot call the native tool by itself. Obtain another real receipt before the adaptive deadline. Reusing a receipt does not reset its age. A missing, expired, replayed or wrong-run receipt stops work. This refresh requirement also applies to manual watcher starts. `watcher ingest --usage-input PATH` only publishes data and never starts a worker or re-enables AGWF.

1. `validate` checks definitions. `activate` takes `objective`, the typed authorization evidence described below, `models` (observed model-to-effort lists), `slot_limit` (total active slots including main), `inventory` (real child IDs/statuses), `observed_at` (Unix time), and optional `session_limit`. Do not invent capability evidence. Activation does not assign or report model settings for the main chat.
2. The pinned candidate starts its private watcher during authorized `activate`/`bind-active-goal`, checks the first healthy sample before committing active state, and starts a new epoch after a valid `resume`. Active workflow/coordination calls renew its 600-second lease. Call `workflow status` at longer work boundaries to renew and read health; if the lease expires or measurement becomes unhealthy, new work is refused and recovery commands remain available. `complete`/`halt` request stop and verify actual worker exit. Manual `watcher start/status/renew/stop` are for diagnostics and work outside an activated workflow, with a fresh run ID. Explicit selection requires the main agent to run and verify the appropriate startup path; no Codex startup hook is installed. Use the private pinned watcher role policy for stale readings and recovery. The sampler calls no model and does not control the current chat. Routine limit checks do not spawn an agent. `usage-due` returns `REUSE_MEASUREMENT` or `READ_USAGE`; set `substantial_work: true` before substantial/parallel work to force a fresh tool reading. `usage` takes `observed_at` and the real tool's raw `rateLimits`. Both windows must exist; unknown readings retry once, then recover. It returns a deadline: 300/120/60/30 seconds at >40/>25/>20/<=20% remaining, shortened to one quarter of estimated time to 20% using per-window observed drain. Reset/old samples do not establish a rate. At <=25% or estimated <=10 minutes, `CHECKPOINT_SOON` means verify a checkpoint of completed work; refresh at completed write batches, not every message. At <=20% or estimated <=120 seconds to that threshold, `SAVE_AND_STOP` freezes dispatch and starts recovery early. `prepare` rejects expired adaptive measurements. No idle polling. Estimates cannot guarantee protection during an uninterruptible call or sudden usage by other chats.
3. `task` takes `id`, `role`, `objective`, `file_inputs`, `context_refs`, `review_targets`, `criteria`, `writes` (exact project-relative file paths, including files to be deleted), `depends_on` and `independent_review` (boolean). Use empty writes for read-only work. Directories are not write claims. `inventory` refreshes real child statuses before each dispatch.
4. `prepare` takes task `id`, optional `effort` and optional pinned `current_context`. It checks models, usage, slots, dependencies and file hashes, reserves capacity and returns actual `collaboration.spawn_agent` arguments with `fork_turns: none`. The message includes the assigned role's own `SKILL.md` and `MEMORY.md`; missing or empty role documents refuse loading and every document is covered by the package manifest. Invoke the prepared arguments exactly. Then `record` takes `id`, `session_id`, `submitted_arguments`, `receipt` (actual tool result), and optional `effective_model`/`effective_effort` from observed metadata. Record failed/uncertain calls with `dispatch_failed`, including `certain_not_started`; uncertain sessions block further work until reconciled using real inventory. Never blindly retry a spawn.
5. `finish` takes `id`, `accepted`, `evidence`, and `review_task` when independent review is required. First observe the session idle/stopped/done via `inventory`; do not release ownership while a writer is running. For review, name the target task ID and revision in verifier `review_targets`: its author is quiescent but acceptance is pending review. Artifact hashes must stay stable across review. Rejected work stays rejected; create a fresh task after resolving the failure. `cancel` releases a never-dispatched ready task with `id` and `reason`. The main coordinator checks user edits before integration. External actions with unknown outcomes are reconciled before retry.

All workflow roles may use only `gpt-6.1-sol`, `gpt-6-astra`, or `gpt-6.1-terra`, with reasoning at least `medium`. The role files pin each model and default effort; no automatic fallback. The main chat uses user-selected client settings and this package does not change an already running model. Candidate prepared dispatch arguments preserve the exact pinned role settings. The retired `astra_coordinator` role is unavailable.

Limit-watcher uses exactly `gpt-6.1-terra`/`medium`. No role has a fallback model. Record actual observed model/effort availability during activation; prepared dispatch fails closed if the exact role setting is unavailable.

## Recovery and stop

### Initial activation retry (v1.1)

The candidate writes `activation-attempt.json` before initial activation and marks it committed only after healthy watcher startup and core commit. A failure response may include `startup_retry.attempt_sha256`; preserve this failure receipt outside the mutable run directory. Repeat the same `activate` or `bind-active-goal` with a fresh real usage input, fresh same-goal observation, original authority and `--startup-attempt-sha256 PRESERVED_FAILURE_PIN`. Do not recompute an edited journal's hash as approval.

| Situation | Supported action |
|---|---|
| Recorded first-start expired telemetry, unchanged identity/state, verified absent worker | Same initial command with external failure pin and fresh post-failure observation/receipt |
| Existing halted workflow, recorded expired telemetry | Existing checked `resume` with `usage_recovery: true`; all post-halt checks apply |
| Quota, early reserve, explicit user stop, another failure, changed/unfinished journal, unknown worker | No technical bypass; preserve evidence and satisfy the applicable continuation/reconciliation rules |

Lifecycle launch/commit/rollback and stop/authority transitions share an owned candidate lock. Do not delete an unexplained `lifecycle.lock`; inspect its actual owner and the incomplete operation. This is not an atomic transaction with native Codex tools. Coordination batches remain sequential, journaled and non-atomic.

Prepare before taking the native reading. Refresh by `sample_at + interval - min(15, interval / 4)` when feasible; this is an early scheduling suggestion, not an extension of receipt validity. Confirm the new sample timestamp, live identity/epoch, heartbeat, sample freshness and lease independently. Ingest alone does not renew the lease. Weekly exceptions use the actual quote and bounded expiry; core and watcher select the same windows while retaining both raw readings.

### Initial native goal binding (N02)

Use `bind-active-goal` when a native goal is already active and initialization has taken longer than the human-source freshness window. It only starts a truly pristine inactive schema2 helper: no tasks, historical operation fields, prior stop/halt/completion, migration or replay reservations. Existing runs use their current authorization and fresh app observations; halted native-bound runs may use a post-halt `paused`/`blocked` observation followed by a newer `active` observation of the same goal. A changed `updated_at` alone does not prove a user status transition. An expired-telemetry interruption of a still-authorized active goal instead uses the technical recovery path below.

Supply `native_binding` with `binding_id`, goal/thread/run IDs, an objective scope with a new scope ID, the exact native `objective`, original native `goal_created_at` and current `observed_at`. Supply command `objective` equal to that exact objective, normal models/capacity/inventory evidence, and a separate `app_goal_observation` containing the same goal/thread/objective/creation/observation time, `status: active`, `source_kind: get_goal` and the actual receipt ID. The observation must be no more than 60 seconds old, with no future timestamp; creation stays original and may be old. Use the exact goal objective text, without descriptive prefixes.

`interpretation` and `procedural_check` are separate nonempty main-authored evidence. Before binding, main must inspect the current authorized goal context and newer human restrictions. Never derive a binding from an old stop, report or policy message; never invent an `exact_quote`, `source_message`, `original_turn_id` or human source creation time. No live/unknown children may remain. The helper checks supplied structure and consistency; main obtains actual native provenance.

The distinct native record and replay history persist across subsequent human resume/activation. Every `app-goal` refresh while the current basis is native must include the original creation and exact objective as well as goal/thread identity. Fresh usage, inventory, capacity, uncertainty and assignment checks remain required. A helper stop/halt remains in effect even if the native goal is still active. Stop, snapshot, halt and verified recovery work normally; `resume` for non-telemetry stops requires either the existing post-halt direct `explicit_goal_continuation` or `native_ui_resume: true` after a post-halt `app-goal` observation of `paused`/`blocked`, followed by a fresh same-goal `active` `get_goal` receipt with Unix `updated_at` strictly later than stop and halt. Same-second ambiguity fails closed. Both paths require checkpoint, usage and inventory checks; native receipts have unknown actor provenance and are single-use.

### Expired telemetry recovery under existing authority

`usage_receipt_expired` means the main agent missed the adaptive receipt deadline. It does not establish exhausted quota. Stop substantive work, save, and halt; the pinned candidate captures the actual same-run/epoch watcher failure during `halt`. Do not supply `usage_failure` yourself to the candidate. Recovery-only coordination batches may stop/snapshot; lifecycle `halt` and `resume` remain direct candidate commands.

For this recorded cause, obtain actual post-halt native usage and a fresh `get_goal` observation of the same active goal, refresh owned-child inventory, and verify checkpoint/current-file hashes and worker exit. Record `workflow usage` and `inventory`, then run `workflow resume --input RECOVERY.json --usage-input USAGE.json`, with `RECOVERY.json` containing only `usage_recovery: true` and `app_goal_observation`. A native-bound observation retains the original objective and goal creation time. No changed `updated_at`, observed inactive status, invented user quote or synthetic click receipt is needed: this path uses the existing authority. The candidate verifies the stored failure still equals the actual watcher latch before launching a new epoch and waits for healthy monitoring. It preserves a bounded weekly exception and the historical SAVE receipt; old tasks are rejected, not implicitly restarted.

The path refuses real quota/early-reserve stops, missing/invalid/other telemetry failures, absent cause records, mismatched goals, stale usage, inactive native goals, live/unknown children, changed checkpoints and explicit user stops not superseded by accepted continuation. It must not change native goal status. A user may make a paused/blocked goal active through Continue; then obtain its actual active observation and apply the same technical checks. Ordinary automatic goal turns can also repair this technical interruption while the same goal remains active. Do not ask for a repeated typed continuation or set `blocked` solely because telemetry expired; apply the native `update_goal` contract. An active status timestamp is not described as proof of who clicked anything. A recorded explicit user stop is superseded only by a successfully accepted direct continuation or, for a currently native-bound run, the existing verified inactive-to-active native UI resume path; `usage_recovery` never supplies that superseding event.

Manual watcher-only runs without a bound native goal do not use workflow `usage_recovery`; they retain the explicit continuation/new-epoch contract. A previous package's halted run with no captured cause is not silently upgraded or relabelled. Preserve its pinned evidence and follow the package update/binding contract; this recovery path applies to cause records captured by this package. Missing provenance must be reported, not manufactured.

### Authorization lifecycle (A26 / AUTH01)

`authorization` is an explicit event object. A plain string, even a nonempty historical `authorization`, is rejected. Legacy state import is unsupported; new work requires a fresh current-package run with current authorization. `interpretation` is a separate top-level string. Preserve the user's exact quote, including punctuation; never concatenate main's interpretation into it. The independent `source_message` projection must match the event's quote and source provenance exactly.

Example continuation payload (synthetic IDs/timestamps; replace with actual observations):

```json
{
  "authorization": {
    "event_id": "user-event-42",
    "kind": "explicit_goal_continuation",
    "exact_quote": "Continue this goal now.",
    "source_kind": "user_goal_continuation",
    "source_id": "user-message-42",
    "goal_id": "goal-7",
    "thread_id": "thread-3",
    "run_id": "run-5",
    "scope": {"kind": "objective", "id": "scope-5", "objective": "Deliver the authorized project change"},
    "observed_at": 1791230401,
    "source_created_at": 1791230401, "original_turn_id": "turn-42", "observed_turn_id": "turn-42"
  },
  "interpretation": "Main classified this source as immediate continuation of the matching objective.",
  "source_message": {
    "source_kind": "user_goal_continuation",
    "source_id": "user-message-42",
    "exact_quote": "Continue this goal now.",
    "source_created_at": 1791230401, "original_turn_id": "turn-42"
  },
  "app_goal_observation": {
    "goal_id": "goal-7", "thread_id": "thread-3", "status": "active",
    "source_kind": "get_goal", "source_id": "actual-goal-tool-receipt",
    "observed_at": 1791230402
  }
}
```

Source kinds are `user_message` or `user_goal_continuation`. IDs and quote must be nonempty strings. Event observations expire after 300 seconds and cannot be future-dated. Event IDs and source messages cannot be consumed twice, including across completed runs. Source message identity is the pair of thread ID and source ID across both source kinds; changing event ID or source kind cannot replay the same underlying user message. App goal observations require matching goal/thread IDs, `get_goal` provenance, a nonempty receipt ID, and a finite timestamp within 60 seconds, no earlier than the event. Before substantive operations, obtain a fresh real app-goal observation and record it with `app-goal`; `task` and `prepare` revalidate the stored observation against the current clock and authorization identity. Age 60 seconds is allowed; age 61 seconds, future timestamps and identity mismatches reject without changing state bytes. Refreshing usage or inventory does not refresh app-goal evidence. All these are **caller-supplied evidence**. Python checks shape, equality, freshness and transition constraints; it does not contact the provider, authenticate a transcript, classify natural language, verify tool receipts, or prove that the quote was genuinely supplied by the user. Main must obtain and preserve real source/tool receipts and classify event kinds correctly. Matching two fabricated quotes would pass equality and is not independent provenance verification.

| Event kind | New activation | Halted/stopped old objective | Dispatch effect |
|---|---|---|---|
| `explicit_task_authorization` | Separate run/scope, matching objective, observed active app goal | Cannot resume | New authorized run only |
| `explicit_goal_continuation` | Separate run/scope allowed with active app evidence | Resume only after all checks below | Fresh tasks after successful resume |
| `future_goal_intent` | Reject | Reject resume | Never authorizes old work |
| `policy_change` | Reject | Reject resume | Never authorizes old work |
| `independent_report_request` | Only a separate scope with `kind: report` and its exact report objective | Reject resume and activation over existing halted run | Separate report run only; old work stays halted |
| `explicit_stop` | Reject | Record with `observe-authorization` for matching identity/scope | Freeze new task/prepare immediately |

`observe-authorization` records future intent, policy changes, separate report requests and scoped stop events without activating/resuming the objective. It does not modify the current authorization. A report for a halted objective runs in a separate helper project/state; it cannot overwrite the halted run to gain access to its tasks. `app-goal` records a fresh observation separately; paused/blocked/stopped/complete observations freeze an active helper. A later active observation alone does not prove a user resume; native UI resume needs a post-halt inactive observation first. For a recorded expired-telemetry halt, use `usage_recovery` under the existing authority instead. `status` returns helper `status` and `app_goal_observation` separately. Dispatch prompts carry authorized scope and goal/thread/run identity.

For the direct user-message resume path, supply a new `explicit_goal_continuation` event observed strictly after stop and halt, matching all stored identities and the exact scope. First read actual usage and actual child inventory after halt. Usage must be fresh, above threshold and within its adaptive deadline; inventory must be fresh and contain no live/unknown owned children. Revalidate checkpoint restore and current-file hashes. Observe the matching app goal active after halt and no earlier than continuation. Degraded recovery requires checkpoint repair. Successful resume rejects old unfinished tasks and permits fresh assignment; it never implicitly restarts a child. Missing, stale, reused, malformed or noncontinuation authorization rejects the command without changing state bytes.

On an explicit user stop, main immediately stops substantive work and new dispatch. Perform only short owned-writer stop/acknowledgement, preservation and halt steps already needed for recovery. Do not create a new plan, extensive handoff or recovery infrastructure during stop. Record app observations separately from helper transitions. Native tools are never intercepted by this helper: main's source classification and native stop discipline remain procedural. A26's real native continuation/stop receipts and an independent audit of unauthorized native operations remain required evidence beyond disposable Python tests.

`stop` freezes dispatch and returns SAVE_ACK requests for running writers. Collect one short acknowledgement per writer. After at most 30 seconds, interrupt unresponsive owned writers if necessary and disclose possible unsaved in-memory content. Before snapshot, establish a quiescent disk state. The helper does not itself send messages, stop processes or provide continuous polling.

`stop` remains available through the pinned candidate when the watcher is unhealthy or has latched `SAVE_AND_STOP`; recovery must not require a healthy measurement first. The direct `stop` -> `snapshot` -> `halt` path and recovery-only coordination batches use the same recovery allowlist. This does not authorize new tasks, clear a SAVE latch, renew an unhealthy lease or resume work. `halt` still verifies quiescent inventory, checkpoint integrity and owned worker exit.

`snapshot` takes `files` (all changed/created/deleted project-relative paths), `next_action` and `writers_quiescent: true` after observing writers stopped writing. Claims from all tasks are included automatically; explicitly include main-coordinator-written and untracked files. Files must have stable hashes while copied. A manifest records absent/deleted paths and a copy of the state. Restore is rehearsed in a fresh internal directory and hashes verified. No credentials are uploaded. Relevant recoverable external artifacts must be saved locally by their owning tools first.

Interrupt owned agents and stop only owned processes through the host tools. `halt` takes a fresh `inventory`, `observed_at`, `owned_processes_stopped: true`, and `stop_evidence` from real tool observations. It rechecks checkpoint and current-file hashes. If snapshot/restore cannot succeed, use `degraded: true` with `reason`, `next_action` and actual stop evidence; never claim verified recovery. `resume` requires one of the telemetry recovery, direct continuation or newer native UI transition paths and all recovery checks described above. On a degraded halt, repair checkpoint first. Never redeem resets or change native goal status automatically; telemetry recovery only restores an already authorized active goal.

`restore` copies a verified checkpoint to a NEW destination outside the project: project contents go under `files/`, while recovery metadata remains outside that subtree. The manifest records paths that should be absent. It never deletes or overwrites live project files. After durable snapshot promotion, retain the current and previous good checkpoints; prune only owned older directories, rejecting links and preserving unknown content. `compact` requires no active children or unfinished tasks and a verified snapshot; it removes completed task records. `complete` closes a delivered run; future work requires a new activation.

## Mechanical coordination and durable dispatch (N05)

`scripts/candidate.py <global pins/options> coordination --input <request.json>` is a standard-library, models-free adapter. A request is `{ "batch_id": "unique_id", "steps": [{ "key": "unique_step", "command": "task", "payload": { ... } }], "seen": [] }`. At most 64 steps execute in order. Each workflow command retains its own validation, state lock and commit; a batch is deliberately non-atomic. Independent reads use command `read` with `payload.paths` containing exact project-relative files. The journal stores read text, byte count and SHA-256; absent files have null pins. It returns one compact decision with blocker, observed session identities, workflow source pin, journal path, outcome map and a result token. Raw request, receipt and result material stays in `.agent-workflow-v1-0/runs/<run-id>/coordination/<batch_id>.json`. Pass previously consumed result tokens in `seen` to suppress unchanged completed results. Native tool output is outside this adapter.

Every step is journaled `pending` with the pre-state hash before execution, then separately `applied` with post-state hash and result, or `failed` with error and post-state hash. A process failure after the state mutation but before result recording leaves `pending`. Restarting that batch returns its blocker without applying another step. Applied steps never execute again; a failed step stops the batch, preserving all earlier outcomes. Never reuse an ID with different requests, erase intent/outcome evidence or infer safe retry from unchanged state bytes: filesystem snapshot/restore effects may already exist. Inspect the durable journal and current core state, preserve the actual external receipts, and use a new bounded reconciliation batch after explicitly resolving the unknown side effect. There is no automatic crash-to-success promotion. The journal lock and core lock protect their respective commits; only main is the writer, and they do not provide a global transaction with other tools. Stale locks require owner inspection before removal.

For the journaled native path:

1. Obtain actual native inventory at the dispatch gate and record `inventory`. `prepare` returns its usual exact native arguments plus an `intent_id`, durably reserved in the core task.
2. Run `dispatch-start` with `id` and `intent_id` immediately before calling the actual native tool. It rechecks authorization/app freshness, usage/SAVE, inventory, task/input validity and assigned write hashes, then records `uncertain` before returning exact `collaboration.spawn_agent` arguments. A timeout, lost result or restart therefore blocks duplicate dispatch. A crash before the native call has the same unknown outcome; inspect actual inventory before resolving it. The existing serial `prepare` / native call / `record` API remains available, but does not have this pre-call uncertainty marker.
3. Main invokes real `collaboration.spawn_agent` directly using the supported tool, never from Python or `functions.exec`. Preserve the actual result. Record fresh inventory with `observation: { "source_kind": "collaboration.list_agents", "source_id": "caller-capture-correlation-id", "evidence_path": "operations/raw-native-inventory.json", "sha256": "<actual-file-hash>" }`. Store the exact raw output once in that project-relative file; state and journal carry only its pointer/pin. Inline `receipt: <actual-native-output>` is also supported instead of the path/hash pair, but duplicates raw output in state/journal. Exactly one variant is allowed. This native provenance projection is mandatory for `dispatch-start` and late-success reconciliation; it does not replace the 60-second TTL or ID/status checks. The core rereads and verifies the evidence pin at every use. `native_inventory(raw)` normalizes supported actual `{agents:[{agent_name,agent_status}]}` output: strings `running` and `idle` preserve their status, `interrupted` becomes `stopped`, and the exact object `{completed: <final text string>}` becomes `done`. Unknown, malformed, ambiguous or duplicate entries reject. Normalized caller inventory must equal the raw projection regardless of ordering; full completed final text stays in evidence.
4. Reconcile the uncertain task with `id`, `evidence`, `no_owned_work_running: false`, exact `submitted_arguments`, actual `session_id`, and actual `receipt`, optionally observed effective model/effort. Receipt must be an object with `id`, `agent_id`, `session_id` or `task_name` equal to the inventory session identity. The observed session must exist with a known status in fresh inventory no earlier than the stored intent. The exact prepared arguments and immutable inputs must still match; reused sessions reject. `Coordination.receipt(...)` journals the actual raw receipt before attempting this transition; CLI callers can submit the same `reconcile` step. Missing, stale, wrong-source, malformed or identity-inconsistent evidence cannot promote a task to running. A late session arriving during stop is recorded for recovery with helper status `stopping`; it does not resume authorization or permit new dispatch. If input invalidation blocks reconciliation, retain receipt/journal and stop the actual child through native tools.
5. Finish only after a new actual terminal inventory at the consequential acceptance gate, preserving independent-review/output-pin checks. Observe actual inventory again for closure/recovery as required by the existing gates. If actual inventory establishes no owned live or unknown work, the existing `reconcile` with `no_owned_work_running: true` rejects the uncertain task; it does not retry it or infer successful work without a receipt.

The helper validates supplied shape, provenance labels, freshness and consistency. It cannot authenticate a caller, native receipt or transcript; a fabricated object with internally consistent native labels is not distinguishable locally. Main must obtain and preserve real native tool output. Where the provider exposes no receipt/call ID, `observation.source_id` is a main-generated capture/correlation ID identifying the one stored raw output, explicitly caller supplied; do not claim it is a provider-issued or authenticated ID. The actual spawn result's agent/session/task identity still must match. A receipt identity check is not metadata authentication. Native prepare/spawn/record is not atomic, and the adapter neither intercepts native tools nor suppresses their output. Journal `source_pin` hashes a canonical map of both workflow.py and coordination.py SHA-256 values.

`collaboration.list_agents` supports `path_prefix` for an already known canonical task prefix; use one gate observation per needed owned group. Unknown roots require an inventory lookup first. Prefix queries may still return full completed finals for matching agents. There is no invented native `compact`, `exclude_completed` or output-filter switch. Local journal result tokens suppress only helper results already delivered, and do not prove provider bytes were filtered.

Run `python -X utf8 -B -m unittest discover -s skills/agent-workflow-v1-0/tests -p test_candidate_coexistence.py -v` from the repository root for actual supported source/staged subprocess entry, guarded batch and lifecycle checks. Historical direct-core fixture traces do not establish candidate readiness. Both paths perform identical task/input pinning, preparation, synthetic receipt recording, synthetic terminal observation, acceptance, verified snapshot and closure. It reports subprocess command counts/exits and actual stdout/stderr bytes. These are modeled main decision boundaries, not measured real main model calls. Synthetic receipts and callbacks are never native dispatch proof; main must separately measure its real serial/batched native paths using actual tool receipts. Timing, temporary absolute path lengths and serialization can change measured byte counts.

## Install and update

Use `tooling/build-candidate.py` to generate the deterministic candidate payload, ZIP and external build receipt. The supported candidate `install --destination <explicit-directory>/agent-workflow-v1-0` verifies every payload byte; unchanged owned content is a no-op. `--update` replaces an unchanged owned installation; edited or unowned content is refused. Failed publication restores the previous directory transactionally. Successful updates keep no previous package or rollback archive. Exact commands and trust-anchor handling are in [runtime binding](coexistence.md).

Implicit skill selection is disabled. Each run's pinned source, staged or installed candidate mapping is its execution identity; do not switch mappings within a run. Its watcher engine, role and instructions are maintained and bundled under `private/limit-watcher`; only the pinned candidate entry controls it. A candidate update uses a new approved run; it does not migrate or rebind existing provenance. Building or installing the package does not itself activate AGWF or register agents. When the user explicitly invokes AGWF for project preparation, the required startup above still applies within that scope. Main-client model selection remains the user's.
